# 知识卡片：如何写一条好的 commit message

### 卡片 1：一次提交只做一件事

**核心知识**：每条 commit 应只包含一件事，混合改动要先拆开再提交。

**简明解释**：功能开发与格式调整混在同一次提交里，会让 review 和回滚都变困难。原文给出的拆分手段是 git add -p 分次暂存。

**例子或自测**：自测——一次改动里既有功能又有格式调整，应该怎么做？参考答案：用 git add -p 拆分，分多次提交。

### 卡片 2：标题行的四条规则

**核心知识**：标题行不超过 50 字符、用祈使语气、不加句号、不用无信息量的词。

**简明解释**：写 "fix login redirect" 而非 "fixed login redirect"；避免 "update"、"fix bug" 这类看不出改动的表述。

**例子或自测**：自测——"fixed login redirect." 违反了哪几条规则？参考答案：用了过去式、加了句号。

### 卡片 3：正文解释"为什么"，不复述"改了什么"

**核心知识**：commit 正文回答改动动机，因为改动内容能从 diff 看到，动机看不到。

**简明解释**：正文与标题之间空一行；每行建议不超过 72 字符。

**例子或自测**：例子——原文的对照：diff 提供"改了什么"，正文提供"为什么改"。

### 卡片 4：用 Closes 关联 issue

**核心知识**：在正文末尾引用 issue，合并后该 issue 会自动关闭。

**简明解释**：原文示例为 "Closes #142"，写法与 issue 编号对应。

**例子或自测**：自测——"Closes #142" 会产生什么效果？参考答案：提交合并后自动关闭 142 号 issue。

### 卡片 5：提交前跑测试比写得漂亮更重要

**核心知识**：提交前先过测试与格式化，否则信息再完整的 commit 价值也是零。

**简明解释**：原文把它定义为习惯而非技巧——说明质量差会抵消说明质量好带来的全部收益。

**例子或自测**：推演例子——一条正文详尽但测试失败的 commit，按原文标准价值为零。
